# ADR-004: Офлайн, очередь правок и слияние конфликтов

**Статус:** Принято (2026-09-23)
**Дата:** 2026-09-23
**Решает:** владелец

## Контекст
Хаб работает с трёх устройств, в том числе без сети. Правки не должны теряться. Одновременные правки с разных устройств не должны молча затирать друг друга. На iOS нет Background Sync, а событие `online` ненадёжно (captive-портал в кафе выглядит как «есть сеть»).

## Решение

### Хранение
- IndexedDB: кэш файлов (содержимое + `sha` + *базовая копия* — версия, с которой начинали правку), blob-ы обложек, очередь правок, токен.
- При первом запуске вызываем `navigator.storage.persist()`, чтобы браузер не вычистил данные при нехватке места.

### Очередь
- **Одна ожидающая правка на файл.** Новая правка того же файла не встаёт в хвост, а обновляет уже ожидающую. Базовая копия остаётся прежней. Так не бывает «второй правки со старым sha».
- **Когда отправляем:** при старте приложения, при `visibilitychange` (вернулись в приложение), по таймеру с нарастающей паузой (5 с → 5 мин), по событию `online` и по кнопке. Работаем только пока приложение открыто. На iOS иначе нельзя, и мы на это не рассчитываем.
- Отправка **строго последовательная** (ADR-002).
- В интерфейсе постоянно виден индикатор: `SYNC · 2 мин назад` / `3 правки ждут отправки` / `нужен новый токен`.
- Есть кнопка «Экспорт несинхронизированного» (JSON-файл). Это страховка на случай, если что-то пошло не так.

### Конфликт (GitHub ответил 409 или 422 на PUT с sha)
1. Перечитываем файл (`no-store`).
2. **Если удалённый sha совпадает с базовым**, конфликт ложный: ветку сдвинул чужой коммит в *другой* файл. Повторяем PUT с паузой, без слияния.
3. **Иначе делаем трёхстороннее слияние** (база / моё / удалённое):
   - скалярные поля: изменилось с одной стороны — берём это изменение; с обеих одинаково — ок; с обеих по-разному — **конфликт поля**;
   - `updatedAt` и подобные служебные метки: берём более позднее, в конфликт не попадают;
   - массивы с id (задачи, вехи, лог, ссылки): сливаются по id. Добавления с обеих сторон сохраняются. Удалено с одной стороны и не менялось с другой — удаляем. Удалено с одной стороны и **изменено** с другой — конфликт элемента (по умолчанию предлагаем «оставить»);
   - порядок массива: берём удалённый порядок и добавляем новые элементы в конец;
   - незнакомые поля сливаются так же, как скаляры (ADR-003).
4. Результат без конфликтов записываем с новым sha.
5. Если конфликты есть, файл уходит во **«Входящие конфликты»**. Это постоянный раздел с бейджем, а не всплывающее окно посреди фоновой синхронизации. Там по каждому полю можно выбрать «моё / с сервера», а для текста — «оба».

### Тесты
Логика слияния — это чистые функции без сети, и они покрываются Vitest в первую очередь: кириллица, эмодзи, удаление против правки, одновременные добавления, битый JSON, `schemaVersion` выше своей.

## Рассмотренные альтернативы
- **Last-write-wins по `updatedAt`:** просто, но молча теряет правки. Нарушает требования.
- **CRDT (Automerge, Yjs):** идеальное слияние, но файлы становятся нечитаемыми для человека и скилла. Нарушает ADR-003.

## Последствия
- Правки не теряются. Спорные места решает владелец, в удобный момент.
- Код слияния — самая сложная часть проекта, поэтому он изолирован и под тестами.
- Этап 6 — не «добавить офлайн», а «подключить очередь к модулю записи». Сам модуль записи с первого дня (этап 4) единый.
