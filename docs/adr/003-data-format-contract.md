# ADR-003: Формат данных как контракт

**Статус:** Принято (2026-09-23)
**Дата:** 2026-09-23
**Решает:** владелец

## Контекст
Файлы данных правят три участника:
- приложение разных версий (на телефоне может висеть старая закэшированная сборка);
- будущий Claude-скилл;
- человек руками.

Любой из них может записать то, чего другой не ожидает. Главный риск — **тихая потеря данных**: старое приложение читает файл нового формата, выбрасывает незнакомые поля и записывает файл обратно уже без них.

## Решение

### Раскладка репо данных
```
projects/<slug>.json   один проект = один файл
ideas/<id>.json        одна идея = один файл (не общий ideas.json — меньше конфликтов)
covers/<slug>.webp     обложки (или .jpg, см. ниже)
settings.json          теги, цвета, порядок, порог «заброшенности» N дней
schema/*.schema.json   JSON Schema — источник правды
README.md              человеческое описание формата
```
`status.json` лежит в отдельной ветке `status` (ADR-005).

> Отличие от исходного ТЗ: вместо общего `ideas.json` каждая идея хранится в своём файле. Идеи быстро кидают с телефона, и один общий файл стал бы постоянным источником конфликтов.

### Правила контракта
1. **`schemaVersion`** (целое число) есть в каждом файле. Если приложение видит версию выше своей, оно показывает файл только для чтения и **никогда его не перезаписывает**.
2. **Незнакомые поля сохраняются.** При чтении, слиянии и записи всё, чего приложение не знает, проходит насквозь без изменений. Ajv без `removeAdditional`, схемы с `additionalProperties: true`.
3. **Сбой изолирован.** Каждый файл проверяется отдельно. Битый файл (синтаксис JSON, нет обязательного поля) становится карточкой «файл повреждён: <ошибка>», остальной хаб работает. Файл, не прошедший проверку, приложение не перезаписывает.
4. **Id у всех элементов массивов** (задачи, вехи, записи лога, ссылки): строка ULID, обязательное поле. Скилл генерирует id так же. Если id нет (ручная правка), приложение при чтении выдаёт временный id и сохраняет его при следующей своей записи.
5. **Slug неизменяемый**: это имя файла. Название (`title`) меняется свободно. Так правки с других устройств никогда не «теряют» файл.
6. **Удаление** проекта — атомарный коммит, который удаляет `projects/<slug>.json` и `covers/<slug>.*`. Защита от воскрешения: приложение пишет файл без `sha` (создание) только для нового проекта. Если файл исчез, а в офлайн-очереди лежит его правка, спрашиваем «проект удалён на другом устройстве — восстановить?». Удаление элементов внутри файла (задача, запись лога) — физическое. Конфликт «удалили здесь, изменили там» решает ADR-004.
7. **Даты:** дедлайны хранятся как `"YYYY-MM-DD"` (локальная дата, без часового пояса) и разбираются как локальные, а не через `new Date(str)`, который считает их UTC. Моменты (`createdAt`, записи лога) хранятся как ISO 8601 со смещением.
8. **Схема** проверяется в трёх местах: в приложении (Ajv), в скилле перед коммитом (тот же файл схемы) и в Action на push в репо данных (стоит минуту Actions, срабатывает только на push не из приложения).

### Обложки
Сжимаем в браузере: `createImageBitmap(file, {imageOrientation: 'from-image'})` (иначе фото с телефона ляжет повёрнутым), максимум 1600 px по ширине, цель до 300 КБ. Safari может молча выдать PNG вместо webp, поэтому проверяем `blob.type` и при необходимости откатываемся на JPEG. Расширение файла соответствует реальному формату, а путь записывается в `project.cover`.

## Рассмотренные альтернативы
- **Один `data.json` на всё:** проще читать, но каждая правка конфликтует со всеми остальными. Отклонено.
- **Строгая схема (`additionalProperties: false`):** ловит опечатки, но ломает совместимость версий. Опечатки ловим предупреждением, а не отказом.

## Последствия
- Старое приложение не портит новые данные, скилл и человек не могут «уронить» хаб.
- Формат чуть многословнее (id, schemaVersion). Это цена надёжности.
- Документацию формата пишем на этапе 9, но черновик схемы появляется уже на этапе 4.
