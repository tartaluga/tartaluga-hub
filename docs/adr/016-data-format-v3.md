# ADR-016: Шапка проекта и страница задачи — расширение формата проекта без смены версии

**Статус:** Предложено (2026-10-04)
**Дата:** 2026-10-04
**Решает:** владелец (что видно и где), Claude (формат, правила записи, проверки)
**Уточняет:** ADR-003 (раскладка репо данных), ADR-009 (поля проекта), ADR-010 п. 3 (группа конфликтов проекта), ADR-007 (`DATA_PATH` в `worker/rules.ts`)

## Контекст
Два решения владельца, которых формат v2 не покрывает:
- **А. Шапка проекта** (G4, 2026-09-25). Отдельная картинка помимо обложки, видна только вверху карточки проекта на всю ширину; на плитках остаётся обложка. Отдельный файл, ставится и удаляется независимо от обложки. Форма — полоса 5:2, как баннер профиля Discord (600×240). Хранится уже вырезанной, как обложка (кадр 16:6, ADR-009).
- **Б. Страница задачи «как в Linear»** (правка 2026-09-26). Открыть задачу и видеть подробности: описание, срок, веха, статус, ссылки. Название меняется карандашом, как название проекта (`InlineText trigger="pencil"`).

Сейчас у задачи есть `id`, `title`, `done`, `due`, `milestoneId`, `doneAt`, `originalDue`. Описания, ссылок и состояния «в работе» нет. Для шапки нет ни поля, ни разрешённого пути.

## Решение

### 1. Версия: `schemaVersion` остаётся 2
Все новые поля необязательные, и ни одно не связано с существующим полем условием, которое старая сборка могла бы нарушить. По правилу 3 из `schema/README.md` версия не растёт. Проверка по аргументу ADR-009 «почему новая версия»:
- старая сборка сохраняет незнакомые поля проекта и задачи (ADR-003 п. 2; `changeItem` в `editProject.ts` меняет только названные поля задачи);
- старая сборка, отметив задачу готовой, оставит `inProgress: true`. Схема это не запрещает (см. п. 3), экраны считают `done` главным, новая сборка уберёт метку при следующей записи. Запись старой сборки сервер не отвергнет;
- старая сборка, удаляя проект, не удалит `banners/<slug>.*` (п. 4). Остаётся файл-сирота без ссылки на него, данные не теряются и не портятся.

Если бы правило «`inProgress` только при `done = false`» было в схеме, старая сборка получала бы непонятный отказ сервера. Тогда понадобилась бы v3, и все проекты стали бы для старых сборок только читаемыми. Это дороже, чем одна лишняя метка, которую никто не показывает.

### 2. Шапка проекта
**Файл:** `banners/<slug>.webp` или `banners/<slug>.jpg` — отдельная папка, а не `covers/<slug>-banner.*`. Причина: slug может содержать дефис. Путь `covers/foo-banner.webp` — это и шапка проекта `foo`, и обложка проекта `foo-banner`. `DATA_PATH` не отличит их, а `projectPaths('foo-banner')` удалил бы шапку чужого проекта. В отдельной папке у каждого пути один хозяин.

**Поле проекта:**
```jsonc
"banner": {
  "description": "Путь к шапке карточки (banners/<slug>.webp или .jpg), полоса 5:2. null или отсутствие — шапки нет (ADR-016).",
  "type": ["string", "null"],
  "pattern": "^banners/[a-z0-9-]+\\.(webp|jpg)$"
}
```

**Картинка:** 5:2, хранится вырезанной, 1500×600. Ширина взята под широкий экран; у Discord 600×240 той же формы. Формат и обработка — те же, что у обложки (этап 8): перекодирование в браузере через canvas в WebP (запасной вариант — JPEG), метаданные EXIF при этом отбрасываются. Лимит сервера на картинку — 2 МБ, как сейчас.

**Сервер** (`worker/rules.ts`): в `DATA_PATH` добавляется `banners/(${SLUG})\.(?:webp|jpg)`, тот же предел длины slug 64. Шапка считается картинкой в лимите `COMMIT_IMAGE_LIMIT` (ADR-012).

**Что видно:**
- Шапка есть — полоса 5:2 вверху карточки проекта над названием, по ширине колонки карточки. На телефоне это вся ширина экрана. На плитках, в «Сегодня» и в поиске шапки нет.
- Шапки нет — карточка как сейчас: без полосы, без заглушки и без пустого места. Генеративная заглушка остаётся только у обложки.
- Файл не читается (404, битая картинка) — как «шапки нет», без ошибки на экране.

### 3. Задача: новые поля
```jsonc
// $defs/task — добавить в properties:
"description": {
  "description": "Подробности задачи, Markdown без сырого HTML (ADR-016).",
  "type": "string",
  "maxLength": 10000
},
"inProgress": {
  "description": "Задача в работе. Значимо только при done = false: при done = true не показывается, хаб при записи убирает (ADR-016).",
  "const": true
},
"links": {
  "type": "array",
  "items": { "$ref": "#/$defs/link" }
}
```
- **Статус — не новое поле `status`, а `done` + `inProgress`.** Три состояния: «к выполнению» (`done: false`, метки нет), «в работе» (`done: false, inProgress: true`), «готово» (`done: true`). `done` остаётся главным: на него опираются прогресс вех, статистика дедлайнов, старые сборки и скилл Claude. Закрытый список вида `status: "todo" | "doing" | "done"` дублировал бы `done`. Тогда понадобились бы условие «`status` ⇔ `done`» в схеме и v3 (п. 1).
- `inProgress` — `const: true`, а не `boolean`: снятие метки удаляет поле, как у `pinned`. Двух способов сказать «не в работе» нет.
- **Ссылки задачи** — тот же `$defs/link`: тот же открытый список `kind`, те же проверки `repo` и `https?://`, ULID у каждой. Слияние уже работает: `mergeValue` сливает id-массив по элементам на любом уровне, где поле — массив объектов с `id`. Значит, `tasks[id].links` сливается поэлементно, как `links` проекта.
- Описание задачи ограничено 10 000 символами: файл проекта не больше 1 МБ (ADR-007), а задач в нём может быть сотня. Описание проекта (20 000, ограничено в клиенте) не меняется.

### 4. Правила записи
| Поле / файл | Кто ставит | Кто убирает |
|---|---|---|
| `banner` + `banners/<slug>.*` | «Поставить шапку»: картинка и проект с `banner` — **один коммит**. Замена с другим расширением — тот же коммит удаляет старый файл | «Убрать шапку»: удаление файла и поля — один коммит. Удаление проекта |
| `tasks[].description` | правка на странице задачи | пустой текст → поле убирается |
| `tasks[].inProgress` | «В работе» на странице задачи | «К выполнению»; `normalizeProject` при `done = true` |
| `tasks[].links` | страница задачи | последняя ссылка удалена → поле убирается (как пустые `links` проекта в `applyEdit`) |

`normalizeProject` дополнительно: у задачи с `done = true` удаляет `inProgress`. Скилл Claude и ручные правки пишут мимо хаба. Экраны не рассчитывают на этот инвариант: при `done = true` метка просто не показывается.

Без `banner` в проекте файл `banners/<slug>.*` хаб не показывает. Это может быть сирота от старой сборки (п. 1) или файл, загруженный мимо хаба. Следующая «Поставить шапку» перезапишет его, удаление проекта уберёт.

### 5. Удаление и конфликты
- **Удаление проекта:** `projectPaths(slug, treePaths)` (`src/data/newProject.ts`) добавляет `banners/<slug>.webp` и `banners/<slug>.jpg`. Как и для обложек, берётся по дереву, а не по полю `banner`: поле мог вписать кто угодно, и оно может указывать на чужой файл. Так же удаляются сироты.
- **Конфликт поля `banner`** в очереди правок — обычный скаляр, «моё / из репо». В список длинного текста (ADR-010 п. 2) он не входит.
- **Конфликт `tasks[id].description`** — длинный текст: выбор по кускам. `conflicts.ts` добавляет путь `tasks/<id>/description` к списку (`description`, `text`, `log/<id>/text`).
- **Вливание ветки** (ADR-010 п. 3): группа проекта — `projects/<slug>.json`, `covers/<slug>.*` и `banners/<slug>.*` вместе. Шапка, изменённая с обеих сторон, — «моя / из `main`», как обложка. Нельзя оставить проект без файла, на который указывает его `banner`, или файл без проекта.

### 6. Страница задачи
- **Адрес:** `#/projects/<slug>/tasks/<taskId>` — вложенный в существующий `projects/:slug`. `taskId` проверяется как ULID. Задачи нет (удалена, неверный id) — «Задача не найдена» и ссылка на карточку проекта, без перехода на `NotFound`.
- **Как открыть:** нажатие на название задачи в карточке проекта. Галочка «готово» в списке работает как сейчас и страницу не открывает.
- **Вид:** отдельная страница на телефоне и на ПК, а не боковая панель. Один маршрут и один компонент, «Назад» браузера и жест «назад» Android работают сами. На ПК — колонка той же ширины, что у карточки проекта. Вверху — путь «Проект › задача».
- **Состав:** название (`InlineText`, карандаш, `draftKey: task:<slug>:<id>:title`), статус — три кнопки-сегмента «К выполнению / В работе / Готово», срок (с «перенесено с …» по `originalDue`), веха (выбор из вех проекта, «без вехи»), описание (Markdown, просмотр и правка, черновик через `draftKey` по ADR-011), ссылки (тот же редактор, что у проекта), «Удалить задачу» с подтверждением.
- **Список задач в карточке:** у задачи «в работе» — метка статуса (цвет «в работе» #6fc2b4), у задачи с описанием или ссылками — значок, что внутри есть подробности.
- Только просмотр (вторая вкладка по ADR-013, файл версии выше 2, ветка без права записи) — все поля без карандашей.

### 7. Безопасность
- `banner` — недоверенный ввод, как `cover`. Схема ограничивает форму пути. Клиент запрашивает файл только если `banner` равен `banners/<slug>.webp` или `banners/<slug>.jpg` своего проекта, иначе считает, что шапки нет. Так проект не покажет чужую картинку и не пошлёт запрос по пути, который вписали вручную. Картинка грузится только через API хаба (`/api/file`), не по внешнему URL. CSP не меняется: `img-src` то же, что у обложек этапа 8.
- `tasks[].description` — Markdown через существующий `Markdown.tsx`: без сырого HTML, ссылки только `https:`/`http:`/`vscode:`.
- `tasks[].links` — те же проверки `href`, что у ссылок проекта; незнакомый `kind` — обычная ссылка с той же проверкой схемы URL.
- `taskId` из адреса — только поиск по массиву, в пути файлов и в запросы не попадает.

## Рассмотренные альтернативы
- **`covers/<slug>-banner.*`** — отклонено: путь двусмысленный при slug с дефисом (п. 2).
- **`schemaVersion: 3`** — отклонено: нет несовместимого изменения. Всем устройствам со старой сборкой пришлось бы ждать обновления, чтобы снова править проекты.
- **Закрытый `status` задачи (`todo`/`doing`/`done`) вместо `done`** — отклонено: ломает старые сборки и скилл, требует v3, дублирует `done`.
- **Открытый список `state` задачи** (как `log.kind`) — отклонено: от статуса зависит логика экранов (прогресс, статистика), незнакомое значение толковать нечем.
- **Боковая панель на ПК** — отклонено пока: два вида одной страницы и собственная логика «назад» ради экрана, где и так одна колонка. Можно добавить позже без смены формата и адреса.
- **Шапка, вырезанная из обложки** — отклонено решением владельца: файлы независимы.

## Последствия
- Старые сборки читают и правят проекты с новыми полями без ограничений. Новых полей они не показывают и при удалении проекта оставляют шапку-сироту.
- Скиллу Claude и проверке схемы в репо данных нужна обновлённая `project.schema.json` : со старой схемой они примут неверный путь `banner` или слишком длинное описание как незнакомые поля, а сервер хаба потом откажет в записи такого проекта.
- Конфликтов в описании задачи станет больше, чем в названии: выбор по кускам уже есть, новых механизмов не нужно.
- Тесты: схема (валидные и невалидные примеры: путь `banner`, `inProgress: false`, ссылка задачи с `javascript:`), `rules.ts` (`banners/...`, `banners/../x`, длинный slug), `projectPaths`, `normalizeProject` (`done` + `inProgress`), `merge` (`tasks[id].links`, `tasks[id].description`), маршрут задачи (неверный id, удалённая задача).

## План работ (в `tasks/todo.md` после принятия)
1. **S** — схема: `banner`, `tasks[].description|inProgress|links`, примеры, `schema/README.md`, генерация `validators.js`/`types.ts`.
2. **S** — сервер: `banners/` в `DATA_PATH`, тесты `rules.ts` и лимита картинок.
3. **S** — `projectPaths` + `banners/`, `normalizeProject` + `inProgress`, `conflicts.ts` + `tasks/<id>/description`, группа вливания ветки + `banners/`.
4. **M** — страница задачи: маршрут, название карандашом, статус, срок, веха, удаление, только просмотр, черновики.
5. **M** — описание и ссылки задачи: редактор Markdown и ссылок, переиспользование из карточки проекта; метки в списке задач.
6. **M** — шапка: загрузка, вырезка 5:2, перекодирование, «Поставить / Убрать шапку», показ в карточке. Делается вместе с обложками этапа 8 и использует тот же конвейер картинок.
7. **S** — схема в скилле Claude и в проверке репо данных.

## Вопросы владельцу
1. **Нужен ли статус «отменена» у задачи?** Варианты: а) нет — ненужную задачу удаляют; б) да — новое поле `cancelled: true` при `done = true`, не считается в статистике «в срок». **По умолчанию — а.** Не блокирует: «б» можно добавить позже без смены версии.
2. **Шапка на широком экране ПК.** Варианты: а) по ширине колонки карточки, 5:2 без обрезки; б) на всю ширину окна, высота ограничена (около 320 px), края по высоте обрезаются. **По умолчанию — а:** шапка хранится уже вырезанной, обрезка при показе ломала бы кадр. Не блокирует формат, только вёрстку задачи 6.
3. **Страница задачи на ПК.** Варианты: а) отдельная страница, как на телефоне; б) боковая панель справа от карточки. **По умолчанию — а** (см. альтернативы). Не блокирует формат и адрес, только задачу 4.
