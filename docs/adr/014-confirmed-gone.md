# ADR-014: «Удалено» — только подтверждённое сервером

**Статус:** Предложено (2026-09-29)
**Дата:** 2026-09-29
**Решает:** владелец
**Уточняет:** ADR-004 (что значит «файл удалили» для очереди), ADR-007 (ответы API сервера)

## Контекст
GitHub отвечает 404 в трёх разных случаях: нет ветки, нет файла — и «токен не видит репо» (установку GitHub App сузили или сняли, репо переименовали, доступ временно потерян). Отличить их по одному ответу нельзя.

До этого решения сервер превращал любой 404 GitHub в `404 not_found «Не найдено в репо данных»`, а неизвестную команду — тоже в `404 not_found`. Клиент по `404 not_found`:
- на ветке ≠ main — стирал очередь, конфликты и кэш ветки (`forgetBranch` в `syncBranch`);
- на записи файла — считал файл удалённым и шёл в слияние, а из него, если 404 повторялся, — во «Входящие конфликты».

Итог: временная потеря доступа к репо данных стирала неотправленные правки ветки. Это долг из глобального ревью 29.09 (`CLAUDE.md`, «Долги»).

## Решение

### 1. Сервер: 404 GitHub проверяется
Каждый обработчик, чей 404 клиент понимает как «удалено», оборачивает обращение к GitHub в `confirmGone` (`worker/gone.ts`). На 404 (и на 422 «does not exist», который `github.ts` тоже считает `not_found`) сервер делает до трёх проверочных запросов:

| Что проверяется | Запросы | Ответ клиенту |
|---|---|---|
| ветка | `GET ref` ветки → 404; `GET` репо → 200 | `404 branch_not_found` |
| файл в ветке (только правка с `sha`) | `GET ref` → есть; `GET contents` → 404; `GET` репо → 200 | `404 not_found` |
| объект по sha (`/api/blob`) | `GET` репо → 200 | `404 not_found` |
| всё прочее: репо не видно, GitHub 5xx или лимит во время проверки, ветка/файл при перепроверке есть | — | `503 upstream_unavailable` |

- Проверка репо — последней: если доступ пропал между запросами, итог — `upstream_unavailable`, а не «удалено».
- Создание файла (без `sha`) проверяет только ветку: файла там и не было, «потерять» его нельзя.
- Где проверять нечего, `index.ts` отдаёт любой непроверенный 404 GitHub как `503 upstream_unavailable` (запрет по умолчанию: «удалено» не выдаётся случайно).
- `/api/status` и `/api/status/refresh` («виджеты не собирались/не настроены») тоже отвечают `404 not_found` только при видимом репо.
- Доп. запросы — только на пути 404, не больше трёх: до лимита Workers Free (50 подзапросов на запрос) далеко.

**Почему два кода, а не один `not_found`.** Ветку и файл клиент обрабатывает по-разному: пропавшая ветка стирает её очередь целиком, пропавший файл — только уводит одну правку в выбор «вернуть или согласиться». Отдельный код `branch_not_found` делает стирание ветки возможным только по ответу нового сервера, который его подтвердил; неоднозначный `not_found` старого сервера ветку больше не стирает. Для файла код `not_found` оставлен: старый клиент понимает его правильно (идёт в слияние, а слияние само сверяется со списком файлов).

### 2. Неизвестная команда — `404 no_route`
Не `not_found`: клиент не должен принять «такой команды нет» (например, запрос старой сборки к переименованному маршруту) за «файла нет».

### 3. Клиент
- `isBranchGone` (`404 branch_not_found`) — единственное основание для `forgetBranch` в сверке ветки. Прочие ошибки, в том числе любой другой 404, ветку не трогают: `sync: 'error'`, повтор при следующей сверке.
- `isGone` (`404 not_found`) — только на первой записи файла: правка уходит в слияние (`mergeAndSend`), которое по свежему списку файлов решает, удалён ли файл (`recordDeleted`) или нет (запись заново).
- В `failed()` любой 404 — временная ошибка (`later`, повтор с растущей паузой). Туда 404 доходит, только если сервер противоречит списку файлов (файл в списке, а запись отвечает «нет»), ветки нет (её сотрёт сверка) или ответ не от API хаба. Раньше такой 404 отправлял правку во «Входящие».
- Синтетические `ApiError(404, 'not_found')` клиента (`session.ts`: нет файла на экране при правке, нет файла при записи выбора в конфликте; `data/ideas.ts`: идеи нет) строятся по списку файлов ветки — это подтверждённое отсутствие. Они только показываются пользователю, ничего по ним не стирается.
- Серверные `not_found` не про репо данных (`account.ts` — нет такого входа, `passkeys.ts` — нет ключа) идут только в текст ошибки на экране «Ключи и входы»; `isGone` там не используется.

### 4. Совместимость при выкатке (ADR-011)
Worker и статика выходят одной сборкой, но открытая вкладка старой сборки какое-то время говорит с новым сервером; при постепенной выкатке Cloudflare возможно и обратное.

| Клиент | Сервер | Ответ | Что делает клиент | Данные |
|---|---|---|---|---|
| старый | новый | `branch_not_found` | не знает кода: 404 без `not_found` — ошибка сверки, ветку не стирает; на записи — повтор позже | целы; ветка стирается после обновления хаба |
| старый | новый | `upstream_unavailable` (503) | временная ошибка, повтор | целы |
| старый | новый | `not_found` (подтверждён) | слияние → по списку файлов «удалён» → выбор во «Входящих» | целы (правка во «Входящих») |
| старый | новый | `no_route` | 404 без `not_found` — временная ошибка | целы |
| новый | старый | `not_found` на сверке ветки | не `branch_not_found` — ветку не стирает | целы |
| новый | старый | `not_found` на записи | слияние по списку файлов; противоречие — повтор, не конфликт | целы |

Ни одна комбинация не стирает очередь по неподтверждённому ответу. Раньше стирала комбинация «старый клиент — старый сервер»; её больше нет после обновления любой из сторон.

## Последствия
- Временная потеря доступа к репо данных видна как «GitHub сейчас не подтверждает данные — повторю позже», очередь и ветки целы.
- Если репо данных действительно удалят или навсегда закроют доступ, хаб будет бесконечно повторять, а не стирать — это намеренно: чинить доступ, а не терять правки.
- Удаление ветки, которую уже удалили в другом месте, на экране «Ветки» показывает «Ветки нет в репо данных» (экран ветвей заморожен, отдельной обработки не добавлено); сверка открытой ветки её забудет.
- Коды ошибок сервера — `ErrorCode` в `worker/http.ts`; новые: `branch_not_found`, `no_route`, `upstream_unavailable`.
- Закрыт долг «`not_found` от сервера неоднозначен» из `CLAUDE.md`.
