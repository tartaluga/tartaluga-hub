# ADR-010: Конфликты v2 — устройство в коммитах, выбор кусков текста, вливание ветки с разбором

**Статус:** Принято (2026-09-25)
**Дата:** 2026-09-24
**Решает:** владелец (что видно и как выбирается), Claude (протокол и проверки)
**Уточняет:** ADR-004 (правило «оба» для текста, индикатор «нужен новый токен»), ADR-007 (вливание ветки только через merge API)

## Контекст
Макеты «Синхронизация и конфликты» показывают то, чего ADR-004 и ADR-007 не дают:
- у версии из репо видно, с какого устройства и когда она записана: «Версия из репо · телефон · 14:05»;
- кнопки «Оба» нет;
- при вливании ветки совпадающие правки уходят во «Входящие конфликты», а по ADR-007 сервер при конфликте отвечает 409 и ничего не делает;
- состояние «Нужен вход · сессия истекла» вместо «нужен новый токен» (токена в браузере с ADR-007 нет).

Владелец решил: устройство в коммитах — да; вместо «Оба» — окно выбора кусков diff, как на GitHub; вливание с конфликтом — как на макете.

## Решение

### 1. Трейлер `Hub-Device` в каждом коммите хаба
- Сервер дописывает к сообщению каждого своего коммита пустую строку и трейлер `Hub-Device: <deviceLabel сессии>`. `deviceLabel` берётся из записи сессии в D1, а не из запроса.
- Сообщение от клиента (`POST /api/commit`) сервер сводит к одной строке: переводы строк заменяются пробелами. Иначе клиент мог бы подделать трейлер.
- Ответ 409 на запись файла и `GET /api/file?path=…&commit=1` возвращают `lastCommit: { at, device }` последнего коммита, менявшего этот путь. Сервер сначала фиксирует голову ветки, потом читает файл и ищет коммит (`commits?path=…&sha=<голова>&per_page=1`) от этой же головы. Иначе метка могла бы относиться не к той версии, что показана. Обычное чтение без `commit=1` лишний запрос к GitHub не делает.
- Трейлеру верим, только если автор коммита на GitHub — бот приложения (`tartaluga-hub[bot]`). Скилл Claude и ручные коммиты идут от других учётных записей и могут написать в сообщении что угодно. Для них `device: null`, интерфейс пишет «из репо · <время>». *Исправлено 2026-09-24 по ревью.*
- Трейлер из репо — всё равно недоверенный ввод: берётся первая строка значения, не длиннее 60 символов, выводится только как текст.

### 2. Длинный текст: выбор по кускам вместо «Оба»
- Поля с длинным текстом заданы списком, а не длиной: `description` проекта, `log[].text`, `text` идеи. Остальные поля в конфликте — две кнопки «моё / из репо».
- Для поля из списка «Входящие конфликты» открывают всплывающее окно. Текст трёх версий (база, моя, из репо) разбит построчно на куски (diff3).
  - Кусок изменён только с одной стороны — выбран заранее в пользу изменившей стороны, его можно переключить.
  - Кусок изменён с обеих сторон — выбор «моя / из репо» обязателен.
  - «Применить» активна, когда выбраны все куски. Внизу виден итоговый текст.
- Однострочный текст — один кусок, то есть те же две кнопки.
- Сравнение — чистая функция без сети (`src/data/textMerge.ts`) с тестами: кириллица, эмодзи, пустые строки, перенос строк `\r\n`.

### 3. Вливание ветки с разбором конфликтов
Прежний путь остаётся первым: merge API GitHub. Если он ответил конфликтом, вместо отказа:
1. Клиент берёт у сервера `GET /api/branches/:name/merge-plan`: `mainHead`, `branchHead`, `mergeBase` (compare API) и пути, изменённые после базы, с отметкой стороны (ветка / `main` / обе) и blob sha каждой версии. Больше 300 изменённых файлов — отказ, как сейчас (`MERGE_FILES_LIMIT`).
2. Для пути, изменённого с обеих сторон, клиент читает три версии и сливает **сырые** файлы по ADR-004 (`src/data/merge.ts`): без подстановок и без выдачи id при разборе. Массив, где хоть у одного элемента нет `id`, сливается как скаляр — это уже правило `merge.ts`. *Исправлено 2026-09-24 по ревью:* `parseFile` выдаёт недостающим элементам случайные ULID, и три версии получили бы разные id, задачи задвоились бы.
   - Обложка (двоичный файл) изменена с обеих сторон — конфликт «моя / из `main`».
   - Файл удалён с одной стороны и изменён с другой — конфликт «оставить / удалить».
   - Конфликты группируются по проекту: `projects/<slug>.json` и `covers/<slug>.*` разбираются вместе, чтобы нельзя было оставить проект без обложки или обложку без проекта.
3. Конфликты уходят во «Входящие конфликты» группой «Вливание ветки <имя>». Пока группа не разобрана, `main` не меняется.
4. После разбора клиент отправляет `POST /api/branches/:name/merge` с `{ mainHead, branchHead, resolved }`. `resolved` содержит **только пути, изменённые с обеих сторон**, и для каждого одно из трёх: `{ text }` (слитый JSON), `{ delete: true }` или `{ blob: <sha> }` (выбор стороны целиком, в том числе для обложек). Двоичные файлы по сети не ходят. Сервер:
   - проверяет, что `branchHead` — текущая голова ветки, а `mainHead` — текущая голова `main`; иначе 409, клиент начинает с шага 1;
   - сам заново строит план от этих голов. Каждый путь из плана «с обеих сторон» должен быть в `resolved`, других путей там быть не должно. `blob` должен совпадать с версией этого пути в `main` или в ветке;
   - изменения с одной стороны берёт сам: blob sha из ветки или удаление;
   - проверяет пути (`rules.ts`) и схемой — каждый JSON-файл итогового дерева, изменённый после базы, а не только присланные;
   - создаёт через Git Data API дерево на основе дерева `mainHead` и один коммит с двумя родителями `[mainHead, branchHead]`, сдвигает `main` без force. На GitHub ветка выглядит влитой.
5. Ветку после вливания не удаляют автоматически, как и сейчас.
6. Вливание через merge API без конфликта теперь тоже проверяет схемой итог, а не только файлы ветки.

### 4. Индикатор «Нужен вход»
Состояние индикатора ADR-004 «нужен новый токен» заменяется на «Нужен вход · сессия истекла»: сервер ответил 401, очередь правок сохраняется до повторного входа.

## Последствия
- «Входящие конфликты» показывают устройство и время удалённой версии без хранения этого на клиенте.
- Выбор по кускам ничего не отбрасывает молча: каждый кусок выбран явно или виден как выбранный заранее. В куске, изменённом с двух сторон, выбор одной стороны сознательно отбрасывает строки другой.
- Вливание с конфликтом — самая тяжёлая часть (L): новый endpoint, коммит с двумя родителями через Git Data API, группа во «Входящих конфликтах». Делается после экрана конфликтов (S2).
- Лишний запрос к GitHub — только на 409 и при открытии конфликта. План вливания стоит 2 запроса compare и по 3 чтения на каждый путь, изменённый с обеих сторон.
- Правило «сливать сырые файлы» касается и очереди правок ADR-004 (задачи E2 и S1): `merge()` получает файлы до `parseFile`.
- Реализация: `worker/write.ts`, `worker/githubApp.ts`, `worker/api.ts` (трейлер, `lastCommit`, merge-plan, merge с разбором); `src/data/textMerge.ts`; экран `Conflicts`.
