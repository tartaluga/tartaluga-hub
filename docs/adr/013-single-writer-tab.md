# ADR-013: Пишет одна вкладка

**Статус:** Принято (2026-09-29)
**Дата:** 2026-09-29
**Решает:** владелец
**Уточняет:** ADR-004 (очередь правок и «Входящие конфликты» на устройстве)

## Контекст
По ADR-004 очередь правок и конфликты лежат в IndexedDB, общей для всех вкладок хаба на устройстве. Сделано было так, что править и отправлять могла каждая вкладка: у каждой своя очередь в памяти, общая — в IndexedDB, между ними две блокировки Web Locks (`hub-queue`, `hub-queue-send`), сверка записей (`reconcile`, `epoch`, `storedIds`) и сообщения по BroadcastChannel.

Глобальное ревью 2026-09-29 (таблица «Перемудрение», строка «Многовкладочность очереди») назвало это самым запутанным кодом проекта. В нём остались два открытых долга:
- удаление неотправленной идеи во вкладке А, пока вкладка Б её отправляет, — идея может вернуться;
- вкладки разных сборок: старая при перечитывании очереди переводит записи новой в конфликты.

Хаб — личный инструмент одного человека. Править одно и то же в двух вкладках одного устройства ему не нужно.

## Решение
1. **Пишущая вкладка.** При старте вкладка просит эксклюзивный Web Lock `hub-writer` без ожидания (`ifAvailable`). Получила — держит его всю жизнь и работает как раньше для одной вкладки: правки, очередь, отправка, сверка, конфликты, черновики и handoff (ADR-011).
2. **Вкладка просмотра.** Не получила — показывает данные с устройства и с сервера, но ничего не пишет: ни в очередь, ни на сервер, ни в IndexedDB (`queue`, `conflicts`, `branchFiles`, `kv`), не мигрирует записи очереди, не читает и не пишет handoff. Все действия, которые пишут, отклоняет одна проверка в сессии (`onlyWriter`, ошибка 423 с текстом «Хаб открыт в другой вкладке — правь там. Здесь только просмотр.»). Сверху плашка `ReadOnlyBanner` с тем же текстом; пока она видна, поля ввода не принимают текст (`lockInputs`: поле в фокусе становится `readOnly`; поиск работает).
3. **Смена пишущей.** Вкладка просмотра ждёт тот же лок обычным запросом. Пишущая закрылась — ждущая получает лок, поднимает очередь и конфликты с устройства (как старт пишущей: записи, которые сборка не понимает, — во «Входящие»), подхватывает черновики из handoff и начинает отправку. Плашка уходит.
4. **Уведомления.** BroadcastChannel `hub-data` остаётся только для сообщений: пишущая после записи на устройство шлёт «перечитай» (вкладки просмотра перечитывают очередь, конфликты и кэш открытой ветки); выход в любой вкладке шлёт «вышли» (остальные стирают своё и показывают вход). Очередь между вкладками больше не сверяется.
5. **Без Web Locks** (браузеров без них у владельца нет: Chrome на ПК и Android, Firefox) вкладка считается пишущей, как раньше одна вкладка.
6. Удалено: блокировки `hub-queue` и `hub-queue-send`, `reconcile`, `epoch`, `storedIds`, учёт удалённых веток между вкладками (`goneAt`), перечитывание очереди перед «Влить».

## Последствия
- Править в двух вкладках одного устройства нельзя: вторая — только просмотр, пока первую не закроют. На разных устройствах всё как по ADR-004.
- Долги «удалённая идея возвращается из-за второй вкладки» и «вкладки разных сборок переводят записи в конфликты» закрыты: пишет одна вкладка, другие очередь не трогают.
- Переходный момент обновления: вкладка старой сборки не знает про `hub-writer` и может писать рядом с новой, пока не перезагрузится. Обновление (ADR-011) перезагружает все вкладки, окно короткое.
- Ветки в интерфейсе заморожены (ADR-012): вкладка просмотра может открыть другую ветку для просмотра, но открытую ветку устройства не меняет.
