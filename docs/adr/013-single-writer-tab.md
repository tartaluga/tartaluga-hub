# ADR-013: Пишет одна вкладка

**Статус:** Принято (2026-09-29)
**Дата:** 2026-09-29
**Решает:** владелец
**Уточняет:** ADR-004 (очередь правок и «Входящие конфликты» на устройстве)

## Контекст
По ADR-004 очередь правок и конфликты лежат в IndexedDB, общей для всех вкладок хаба на устройстве. Сделано было так, что править и отправлять могла каждая вкладка: у каждой своя очередь в памяти, общая — в IndexedDB, между ними две блокировки Web Locks (`hub-queue`, `hub-queue-send`), сверка записей (`reconcile`, `epoch`, `storedIds`) и сообщения по BroadcastChannel.

Глобальное ревью 2026-09-29 (таблица «Перемудрение», строка «Многовкладочность очереди») назвало это самым запутанным кодом проекта. В нём остались два открытых долга:
- удаление неотправленной идеи во вкладке А, пока вкладка Б её отправляет, — идея может вернуться;
- вкладки разных сборок: старая при перечитывании очереди переводит записи новой в конфликты.

Хаб — личный инструмент одного человека. Править одно и то же в двух вкладках одного устройства ему не нужно.

## Решение
1. **Пишущая вкладка.** При старте вкладка просит эксклюзивный Web Lock `hub-writer` без ожидания (`ifAvailable`). Получила — держит его всю жизнь и работает как раньше для одной вкладки: правки, очередь, отправка, сверка, конфликты, черновики и handoff (ADR-011).
2. **Вкладка просмотра.** Не получила — показывает данные с устройства и с сервера, но ничего не пишет: ни в очередь, ни на сервер, ни в IndexedDB (`queue`, `conflicts`, `branchFiles`, `kv`), не мигрирует записи очереди, не читает и не пишет handoff. Все действия, которые пишут, отклоняет проверка на входе (`onlyWriter` в сессии, `assertWriter` для «Сделать проектом» и создания ветки; ошибка 423 с текстом «Хаб открыт в другой вкладке — правь там. Здесь только просмотр.»). Вторая проверка — на самой записи: `applyWrite`, цепочка записей в IndexedDB (`persist`) и запись на сервер (`writeRemote`) отказывают, если лок у другой вкладки или сессию стёрли «Выйти». Сверху плашка `ReadOnlyBanner` с тем же текстом; пока она видна, поля ввода не принимают текст (`lockInputs`: поле в фокусе становится `readOnly`; поиск работает).
3. **Смена пишущей.** Вкладка просмотра ждёт тот же лок обычным запросом. Пишущая закрылась — ждущая получает лок, дожидается конца своего старта, поднимает очередь и конфликты с устройства (как старт пишущей: записи, которые сборка не понимает, — во «Входящие») и только после этого снимает просмотр, подхватывает черновики из handoff и начинает отправку. Плашка уходит.
4. **«Писать здесь».** Кнопка на плашке шлёт по BroadcastChannel `takeover`. Пишущая перестаёт принимать правки и дожидается всего принятого: отправки очереди, записей настроек и прямых записей (разбор конфликта, удаление, тег, «Сделать проектом» — их считает `onlyWriter`) и записей на устройство. Правку, не легшую на устройство, она пробует записать ещё раз; не вышло — не уступает и отвечает `takeoverRefused` (у просящей на плашке «не может уступить»). Иначе сохраняет черновики в handoff (тот же механизм, что при обновлении, ADR-011), отпускает лок, сама вставая за ним в очередь, и только после этого становится просмотром; отпустить нечего (нет Web Locks) — тоже отказ. Лишний второй лок уже пишущей вкладке сразу отпускается. Остальные вкладки просмотра встают в конец очереди, пропуская просящую. Просящая получает лок и забирает черновики. Нет ответа за 5 с (вкладка заморожена, например в фоне на Android) — на плашке «Другая вкладка не ответила — закрой её или нажми ещё раз», кнопка снова активна. Одновременные нажатия в двух вкладках протокол не разводит: лок получит одна, вторая останется просмотром. Лок не отнимается (`steal`): проснувшаяся вкладка, у которой отняли лок посреди записи, опаснее, чем просьба закрыть её.
5. **Обновление с двумя вкладками.** Новая версия перезагружает обе вкладки (ADR-011). Пишущей становится та, что стартовала первой, а черновики из handoff забирает только пишущая. Если на экране оказалась вкладка просмотра, владелец жмёт «Писать здесь»: пишущая сохраняет свои черновики в handoff, и они появляются в этой вкладке.
6. **Уведомления.** BroadcastChannel `hub-data` остаётся только для сообщений: пишущая после записи на устройство шлёт «перечитай» (вкладки просмотра перечитывают очередь, конфликты и кэш открытой ветки); выход в любой вкладке шлёт «вышли» (остальные стирают своё и показывают вход). После «Выйти» ответы уже отправленных запросов на устройство не пишутся — до нового старта сессии. Очередь между вкладками больше не сверяется.
7. **Без Web Locks** (браузеров без них у владельца нет: Chrome на ПК и Android, Firefox) или если браузер отказал в них (промисом или исключением), вкладка считается пишущей, как раньше одна вкладка. Тогда две такие вкладки могут перезаписать правки друг друга в очереди — защиты нет; на целевых браузерах Web Locks есть.
8. Удалено: блокировки `hub-queue` и `hub-queue-send`, `reconcile`, `epoch`, `storedIds`, учёт удалённых веток между вкладками (`goneAt`), перечитывание очереди перед «Влить».

## Последствия
- Править в двух вкладках одного устройства нельзя: вторая — только просмотр, пока первую не закроют. На разных устройствах всё как по ADR-004.
- Долги «удалённая идея возвращается из-за второй вкладки» и «вкладки разных сборок переводят записи в конфликты» закрыты: пишет одна вкладка, другие очередь не трогают.
- Переходный момент обновления: вкладка старой сборки не знает про `hub-writer` и может писать рядом с новой, пока не перезагрузится. Обновление (ADR-011) перезагружает все вкладки, окно короткое.
- Ветки в интерфейсе заморожены (ADR-012): вкладка просмотра может открыть другую ветку для просмотра, но открытую ветку устройства не меняет.
