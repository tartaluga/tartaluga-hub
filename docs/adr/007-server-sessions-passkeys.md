# ADR-007: Сервер на Cloudflare Workers, сессии и вход по ключу доступа

**Статус:** Принято (2026-09-23). Второе мнение другой модели владелец решил не запрашивать; дизайн проверен ревьюером-агентом и скиллами security-and-hardening и security-audit
**Дата:** 2026-09-23
**Решает:** владелец
**Заменяет:** ADR-001 целиком (хостинг) и часть ADR-002: токен в браузере и прямые запросы браузера к GitHub. Механика работы с GitHub из ADR-002 остаётся, но выполняется на сервере: чтение дерева одним запросом, запись по одной, атомарные коммиты, base64 через TextEncoder.

*Исправлено 2026-09-23 после адверсариального ревью безопасности (16 находок):*
- узкий прокси к GitHub заменён смысловым API;
- добавление ключа требует свежего входа;
- деплой без токена Cloudflare в GitHub;
- ключи доступа привязаны к точному адресу, превью-адреса отключены;
- CSP без `unsafe-inline`;
- план безопасного съезда со старой версии.

У владельца нет iPhone; причины переезда уточнены.

*Исправлено 2026-09-23 по решению владельца:*
- хаб работает с ветками репо данных: переключение, создание, удаление, слияние в `main`, чтение `status`;
- коммиты — только в репо данных, никогда в репо проектов;
- зачем теперь нужна организация `tartaluga`.

## Контекст
По ADR-002 fine-grained токен GitHub лежит в IndexedDB браузера. Владелец хочет «как в нормальных сервисах»: главный ключ к данным живёт на сервере, устройство получает только сессию. Плюс вход по ключу доступа (passkey): отпечаток, Windows Hello. Устройства: ПК и ноутбук на Windows, Android-телефон.

Ограничения: бесплатно, минимум движущихся частей, установленное PWA, офлайн-режим сохраняется.

**Почему сайт тоже переезжает с GitHub Pages.** Сессия — это cookie. Если сайт на `tartaluga.github.io`, а сервер на `*.workers.dev`, cookie сервера для сайта сторонняя. Firefox разделяет такие cookie по сайтам: вход через GitHub записал бы сессию в один «ящик», а запросы хаба читали бы другой. Brave и режим инкогнито сторонние cookie блокируют. Кроме того, GitHub Pages не даёт ставить HTTP-заголовки безопасности. Надёжно только одно: сайт и сервер на одном адресе.

## Решение

### Хостинг
- Один Cloudflare Worker отдаёт приложение (static assets) и API под `/api/`. Адрес — `https://hub.<поддомен>.workers.dev`.
- **Превью-адреса отключены** (`preview_urls = false`): иначе старые сборки остаются доступны с теми же секретами.
- **На этом поддомене аккаунта больше ничего не деплоим.** Все Worker'ы одного поддомена — один «сайт» для браузера: они обходят `SameSite` друг друга.
- Заголовки безопасности для статики — файл `_headers`, для API — сам Worker:
  - CSP: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`;
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy`;
  - `'unsafe-inline'` для стилей не нужен: Motion и React ставят стили через CSSOM, CSP это не блокирует. Проверяется на сборке.
  - HSTS не нужен: `.dev` целиком в списке HSTS preload.

### Доступ сервера к данным — GitHub App
- Приложение GitHub «Tartaluga Hub». Владелец — организация `tartaluga`, установлено **только на `tartaluga-hub-data`**. Права: Contents — read/write, Actions — read/write, Metadata — read. **Без Workflows.**
- Worker подписывает JWT (RS256, `iat` на 60 с в прошлом, `exp` ≤ 10 мин) приватным ключом приложения и получает токен установки, который **живёт 1 час**. Токен кэшируется в памяти изолята и перевыпускается заранее. GitHub выдаёт ключ в формате PKCS#1; Worker сам переупаковывает его в PKCS#8, так что владельцу не нужны никакие команды.
- Ключ приложения — секрет Worker. В браузер он не попадает никогда.
- **Зачем теперь организация.** Причина из ADR-001 (отдельный origin для `github.io`) с переездом отпадает. Организация остаётся по двум причинам:
  1. приватное GitHub App организации **физически нельзя установить** на личные репо владельца, так что право записи не дотянется до его проектов даже при ошибке настройки;
  2. у организации свой лимит минут Actions, и cron виджетов не задевает CI личных приватных репо.
- **Хаб пишет только в репо данных.** В репо проектов — никогда. Их коммиты и статусы собирает cron-Action (ADR-005) с токеном только на чтение.

### API — смысловые команды, а не прокси
Браузер не может составить произвольный запрос к GitHub. Worker предоставляет только:

| Команда | Что делает сервер |
|---|---|
| `GET /api/branches` | список веток репо данных: имя, последний коммит, отметки «основная» и «служебная» |
| `POST /api/branches` | `{name}` — создать ветку от текущего `main` |
| `DELETE /api/branches/:name` | удалить ветку (не `main` и не `status`), требует свежего входа |
| `POST /api/branches/:name/merge` | влить ветку в `main` (merge API GitHub). Конфликт → 409 со списком файлов, ничего не меняется |
| `GET /api/files?branch=` | дерево ветки одним запросом: пути, sha, `head` |
| `GET /api/blob/:sha` | содержимое файла по sha (sha — 40 hex-символов, иначе 400) |
| `GET /api/status` | `status.json` из ветки `status` (живые виджеты), только чтение |
| `PUT /api/file` | `{branch, path, text, sha?}` — создать или обновить **один** файл данных |
| `POST /api/commit` | `{branch, changes:[{path, text\|base64\|null}], expectedHead}` — атомарный коммит (новый проект с обложкой, «идея → проект», удаление) |
| `POST /api/status/refresh` | запустить `status.yml` на `main` без входных параметров |

Правила на сервере:
- **Пути** — только из разрешённого списка: `projects/<slug>.json`, `ideas/<ulid>.json`, `settings.json`, `covers/<slug>.(webp|jpg)`. Путь проверяется целиком регулярным выражением (никаких `..`, `%2e`, `.github/`). URL к GitHub сервер собирает сам.
- **Ветки:**
  - имя проверяется по шаблону `^[a-z0-9][a-z0-9-]{0,39}$`: строчная латиница, цифры, дефис, без `/`, `..` и пробелов. Без параметра — `main`;
  - `status` — только чтение: запись, удаление и слияние в неё запрещены, её пишет только Action;
  - `main` нельзя удалить;
  - новые ветки создаются только от `main`;
  - слияние — только «ветка → `main`» через merge API GitHub, который сам отказывает при конфликте;
  - **перед слиянием сервер проверяет схемой каждый изменённый файл данных** (список берёт из compare API). В ветку мог писать Claude-скилл напрямую через git, минуя проверки. Если есть битые файлы, хаб показывает их список и ничего не вливает;
  - **никакого `force` ни для какой ветки**, история не переписывается;
  - `status.yml` запускается только с `main`: на другой ветке могла бы лежать старая версия workflow.
- **Каждый JSON-файл перед записью проверяется** теми же сгенерированными проверяльщиками схемы (ADR-003). Worker тоже запрещает `eval`, поэтому подходят именно заранее сгенерированные. Битый JSON в репо от приложения попасть не может.
- **Каждая запись несёт ожидаемую версию:** `sha` файла или `expectedHead`. При расхождении — 409, дальше слияние по ADR-004. Сервер никогда не повторяет запись «поверх свежего sha» сам.
- **Ответы API:** всегда `Content-Type: application/json`, `Cache-Control: no-store`, `nosniff`. Содержимое файлов приходит внутри JSON, а не «как есть» с типом от GitHub. Так файл из репо не может выполниться на нашем адресе как HTML или SVG.

Уже написанный `GitHubClient` переезжает в Worker почти без изменений. В браузере остаётся тонкий клиент к этим командам.

### Вход
1. **По ключу доступа — основной способ.** Ключи discoverable, `userVerification: required`. `rpId` — **точный хост** `hub.<поддомен>.workers.dev`, `expectedOrigin` — `https://hub.<поддомен>.workers.dev`. Библиотеки: `@simplewebauthn/server` в Worker, `@simplewebauthn/browser` в приложении.
2. **Через GitHub — первое устройство и восстановление.** OAuth того же GitHub App, с `state` и PKCE. Пускает только владельца по **числовому id** GitHub. Токен пользователя GitHub нужен только чтобы узнать id: сервер сразу его отзывает и нигде не хранит.
3. **Добавить ключ можно только при свежем входе:** не старше 5 минут, через GitHub или существующим ключом. Украденная сессия ключ не добавит. `excludeCredentials` не даёт зарегистрировать тот же ключ дважды. Каждое добавление ключа и каждый вход через GitHub попадают в журнал «Безопасность» и показываются плашкой при следующем входе.
4. **«Ключи и входы»:** список ключей с датой последнего использования, удаление ключа, «Выйти везде». Удаление и «Выйти везде» тоже требуют свежего входа. Формулировки честные: ключ в Google Password Manager синхронизируется между устройствами, поэтому удаление ключа отключает его везде.

**Компромисс, записанный явно:** вход через GitHub всегда доступен, иначе при потере всех ключей хаб закрыт навсегда. Значит, защищённость хаба не выше защищённости аккаунта GitHub. Рекомендация владельцу: включить на GitHub вход по ключу доступа или 2FA-приложение.

### Сессия
- Случайный 256-битный id. В D1 хранится только SHA-256 от него.
- Cookie `__Host-hub_session`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, без `Domain`.
- Срок 30 дней со скользящим продлением, но не больше 90 дней от входа.
- Временные данные входа (`state` и PKCE для GitHub, вызов WebAuthn) — **в короткой подписанной cookie** (HMAC, 5 минут), а не в базе. Анонимные запросы ничего не пишут в D1, поэтому их нельзя использовать, чтобы исчерпать лимиты. Cookie для GitHub — `SameSite=Lax`, иначе браузер не пришлёт её при возврате с github.com.
- Защита от подделки запросов: `SameSite=Strict`, точная проверка `Origin` и обязательный заголовок `X-Hub: 1` на всех изменяющих запросах.

### Хранилище сервера — Cloudflare D1
Отзыв сессии или ключа действует сразу. Таблицы:
- `sessions` (хэш, сроки, устройство, последнее использование);
- `passkeys` (id, публичный ключ, счётчик, transports, имя, даты). Счётчик 0 у синхронизируемых ключей — норма, а не признак клонирования;
- `security_log` (события входа и изменения ключей).

Ограничение частоты неудачных входов — встроенный Rate Limiting binding Workers, если он есть на бесплатном плане; иначе — счётчик только для неудачных проверок подписи.

### Офлайн
- Кэш данных в IndexedDB остаётся (ADR-004): без сети хаб показывает последние данные, правки копятся.
- **Кэш и очередь правок — отдельно для каждой ветки.** Правка, сделанная на ветке-эксперименте, уходит только в неё, даже если к моменту появления сети хаб переключили на `main`.
- **На любой ветке, кроме `main`, в интерфейсе постоянно видна плашка** «ветка: <имя>». Иначе легко забыть, что правишь черновик.
- Если сессия истекла без сети, после появления связи хаб просит приложить палец, а очередь ждёт.
- «Выйти» предупреждает, если есть неотправленные правки, и только потом стирает кэш.
- **Честно о пределах:** скачанные проекты на разблокированном устройстве видны через F12. Так устроен любой офлайн-режим. Сервер защищает главный ключ к репо, а не уже скачанные данные.

### Деплой
- **Cloudflare Workers Builds** — встроенная связка Cloudflare с GitHub. Сборку делает Cloudflare по push в `main`; команда сборки включает проверку схемы и тесты.
- **Токена Cloudflare в GitHub нет вообще.** Раньше предлагалось хранить его в секретах публичного репо, но тот, у кого этот токен, может задеплоить код, читающий ключ приложения. Такой токен так же ценен, как сам ключ.
- Миграции D1 — файлы в репо. Применяются **вручную** (`wrangler d1 migrations apply`) после одобрения владельца и с предварительным экспортом базы. Не автоматически.
- В оставшихся GitHub Actions: actions закреплены по SHA коммита, `npm ci` по lock-файлу, `pull_request_target` запрещён.

### Съезд со старой версии (github.io)
1. Последний релиз github.io:
   - отправляет неотправленные правки;
   - стирает токен и IndexedDB;
   - снимает service worker;
   - показывает «Хаб переехал» со ссылкой на новый адрес.
2. Владелец **отзывает fine-grained токен на GitHub сразу**, не дожидаясь, пока обновятся устройства.
3. Через неделю GitHub Pages отключаем, а репо приложения переименовываем из `tartaluga.github.io` в `tartaluga-hub`.
4. На каждом устройстве: удалить старое установленное приложение и поставить новое.

### Что не меняется
- Раскладка репо данных, схема, ADR-003, ADR-004.
- Claude-скилл по-прежнему правит репо данных напрямую через git, минуя сервер. Конфликты с ним ловятся по sha, как с любым другим устройством.
- ADR-005 (cron-виджеты) не меняется. Уточнение для реализации: `status.json` пишет встроенный `GITHUB_TOKEN` workflow с правом `contents: write`, а read-only токен статуса только читает чужие репо. Workflow не выполняет кода из путей, которые может менять приложение (скрипт целиком внутри `status.yml`). При ошибке workflow пишет её в `status.json`, и хаб показывает «виджеты не обновлялись N часов».

## Модель угроз (STRIDE)

*Добавлено 2026-09-23 после проверки скиллами `security-and-hardening` и `security-audit` (точечный режим).*

**Что защищаем:**
- ключ GitHub App: полный доступ на запись к данным;
- сессии и ключи доступа;
- сами данные проектов;
- токен статуса в репо данных: чтение приватных репо владельца.

**Границы доверия:**
1. браузер ↔ Worker;
2. Worker ↔ GitHub API;
3. возврат с github.com (OAuth);
4. данные из репо ↔ интерфейс.

Последняя граница легко забывается. В файлы данных пишет не только хаб, но и Claude-скилл, и человек руками. Доверие определяется тем, **кто написал** значение, а не тем, откуда оно пришло. Поэтому всё из репо — недоверенный ввод для интерфейса.

| Угроза | Где | Мера |
|---|---|---|
| **S** — подмена | вход через GitHub | `state` сверяется с подписанной cookie, PKCE, точный `redirect_uri`, проверка числового id владельца при **каждом** создании сессии |
| **S** — фиксация сессии | любой вход | при каждом входе и каждом «свежем входе» выдаётся **новый** id сессии, старый удаляется |
| **T** — подделка данных | API записи | пути из разрешённого списка, проверка схемой, ожидаемый sha или `expectedHead`, имя ветки по шаблону, `status` только для чтения, без `force` |
| **T** — подмена workflow | ветки | `status.yml` запускается только с `main`. Пути `.github/` приложение писать не может ни в какой ветке |
| **T** — хранимый XSS из данных | ссылки, описание | `href` только со схемами `https:`, `http:` и `vscode:` (последнюю хаб собирает сам из пути к папке). `javascript:`, `data:` и прочие показываются текстом. Markdown в описании — без сырого HTML, с той же проверкой ссылок. Обложка — только путь `covers/…`, никаких внешних URL |
| **R** — отказ от действий | ключи, входы | `security_log`: вход (способ, устройство), добавление и удаление ключа, «Выйти везде», неудачные проверки подписи |
| **I** — раскрытие | ответы API | наружу только коды ошибок и тексты хаба, без тел ответов GitHub и без стеков. `Cache-Control: no-store` |
| **I** — раскрытие | выход | ответ на «Выйти» несёт `Clear-Site-Data: "cache", "storage"`: браузер сам стирает кэш и IndexedDB, даже если скрипт не успел |
| **D** — отказ в обслуживании | API | размер тела: JSON до 1 МБ, картинка до 2 МБ, в одном коммите до 20 файлов. Анонимные запросы не пишут в D1. Ограничение частоты неудачных входов |
| **E** — повышение прав | API | запрет по умолчанию: каждый маршрут, кроме входа и статики, требует действующую сессию, иначе 401. Добавление ключа и удаление ключей — только при свежем входе |

**Личные данные в D1** — минимум с понятным сроком хранения:
- IP не храним;
- «устройство» — это только браузер и ОС из User-Agent, для списка входов;
- истёкшие сессии и вызовы удаляет ежедневный Cron Trigger Worker'а;
- `security_log` хранится 180 дней.

Аналитики и сторонних сервисов нет.

**Жизненный цикл секретов:**
- `.pem` ключ GitHub App владелец вставляет в секреты Cloudflare через панель и **удаляет файл** с диска. В `.gitignore` репо приложения есть `*.pem`, `.dev.vars` и `.env*`.
- Смена ключа: GitHub App позволяет держать два ключа одновременно. Сначала добавляем новый, потом удаляем старый — без простоя.
- Секрет подписи cookie (HMAC) — случайные 32 байта в секретах Worker. Меняется, если что-то пошло не так, и заодно разлогинивает все незавершённые входы.

**Цепочка поставок:**
- в сборке `npm ci --ignore-scripts` (сейчас ни у одного пакета нет скриптов установки — проверено) и `npm audit --audit-level=high`: сборка падает на известных серьёзных уязвимостях;
- `npm audit signatures`: подписи и происхождение пакетов подтверждены, 132 пакета проверены;
- новые зависимости (`@simplewebauthn/*`) проверяются перед добавлением: владелец пакета, возраст релиза, происхождение.

**Промт-карточка** («Скопировать контекст для Claude»): текст проектов может содержать инструкции, адресованные модели. Карточка — обычный текст, который владелец видит перед вставкой. Хаб сам никуда его не отправляет. Риск низкий, записан для полноты.

## Рассмотренные варианты
- **А. Токен в браузере (ADR-002).** Отклонено владельцем: главный ключ на устройстве.
- **Б1. Сайт на Pages, сервер на Workers, сессия в cookie.** Отклонено: сторонние cookie ломаются в Firefox, Brave и инкогнито.
- **Б2. Сайт на Pages, сервер отдаёт короткий токен в JavaScript.** Отклонено: это снова токен в хранилище браузера.
- **Б3. Свой домен (около $10 в год).** Можно позже. Но ключи доступа привязаны к адресу, так что после смены домена их надо добавить заново.
- **Прокси к GitHub API со списком разрешённых путей.** Было в первой редакции. Отклонено после ревью: обходится через `..` в пути, поля тела запроса (`force`, `branch`, `inputs`) и деревья git, и украденная сессия могла бы добраться до токена статуса.
- **Деплой через GitHub Action с токеном Cloudflare.** Отклонено: токен в публичном репо равен ключу приложения.
- **Supabase / Firebase Auth.** Второй поставщик, избыточно для одного владельца.

## Последствия
- **Проще:**
  - главный ключ только на сервере, токены GitHub живут час;
  - вход пальцем, сессии и ключи отзываются;
  - настоящие заголовки безопасности, строгая CSP;
  - сервер проверяет каждый записываемый файл по схеме.
- **Сложнее:**
  - вторая платформа и серверный код;
  - разовые шаги владельца: аккаунт Cloudflare, GitHub App, секреты, связка сборки, отзыв старого токена, переустановка PWA на устройствах;
  - новый адрес;
  - миграции базы вручную.
- **Пересмотреть:**
  - свой домен;
  - отдельный аккаунт Cloudflare, если на поддомене понадобятся другие Worker'ы;
  - перенос cron-виджетов в Cron Triggers.
